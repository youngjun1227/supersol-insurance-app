# 9/11 정성평가 — 기존 슈퍼쏠 vs 우리 구현

> 참가자에게 **같은 과제 4개**를 두 앱에서 시키고, 성공률과 주관 평가를 비교한다.
> 이 폴더는 그 **자료 보관소**다. 운영 절차(리허설·백업·접속 정보)는
> [`../운영/9-11-리허설-체크리스트.md`](../운영/9-11-리허설-체크리스트.md) 가 계속 원본이다.

## 진행 방향

**[`진행계획.md`](진행계획.md) 가 이 조사의 설계 문서다** — 무엇을 재는지, 참가자를 어떻게
고르는지, 20~30분을 어떻게 쓰는지, 결과를 어떻게 말하는지. 먼저 읽는다.

| `평가도구/` | **우리가 만드는 것** — 평가지, 진행자 스크립트, 동의서, 채점 기준 | ✅ |

| `분석결과/` | **우리가 뽑은 것** — 집계표, 발표용 수치·그래프 | ✅ |

### ⚠️ `응답원본/` 은 커밋하지 않는다

**이 저장소는 public 이다.** 참가자 실명·음성·필적이 올라가면 되돌릴 수 없다 —
`git rm` 을 해도 히스토리에 남는다. `.gitignore` 로 막아 뒀고, `.gitkeep` 과
`서식/` 만 추적한다.

- 원본은 **로컬 + 팀 드라이브**에 둔다
- 저장소에 올리는 건 `분석결과/` 의 **집계된 수치**뿐이다
- 집계표에도 참가자는 `P1`·`P2` 로만 쓴다 (목데이터 실명 금지와 같은 이유)

## 무엇을 재나 — 이미 정해진 것

변경로그 §"지표 위상 재정의"(2026-08-27 팀장)가 원본이다. 여기서 바꾸지 않는다.

| 지표 | 비교에 쓰나 | 측정 방법 |
|---|---|---|
| **과제 성공률** | ✅ 주 근거 | 양쪽 동일 — 도착 여부 + 구두 응답 |
| **주관 평가(평가지)** | ✅ 주 근거 | 양쪽 동일 |
| 클릭 수 · 시간 | ❌ **비교 안 함** | 우리 쪽만 자동 — 내부 진단용 |

**왜 클릭 수를 뺐나:** 기존 슈퍼쏠은 남의 앱이라 코드를 못 건드린다. 한쪽은 기계가
정확히 세고 한쪽은 진행자가 눈으로 세면, 그 차이 자체가 **우리에게 유리한 편향**이
된다. 발표에서 방법론을 물으면 무너지는 자리라 아예 비교에서 뺐다.

## 과제 4개 (변경로그 §1 — ★문구 확정 대기)

순서 고정: `premium` → `claim` → `diagnosis` → `product`.
학습 효과는 과제 순서가 아니라 **기존 앱/우리 구현 순서를 참가자 절반씩 교차**해서 통제한다.

| taskId | 과제 | 성공 판정 |
|---|---|---|
| `premium` | "이번 달 내는 보험료가 얼마인지 확인해 주세요" | 도착 + **35,000원** 구두 응답 |
| `claim` | "병원 결제 알림을 보고 보험금 청구를 진행해 주세요" | `/claim/guide` 도착 |
| `diagnosis` | "내 보험 보장이 충분한지 확인해 주세요" | `/diagnosis` 도착 + 부족 항목 언급 |
| `product` | "치아 보장 보험을 찾아 비교해 주세요" | S6-A 도착 |

⚠️ **기존 슈퍼쏠에는 `diagnosis` 에 대응하는 화면이 없다.** 이건 결함이 아니라
우리 논지 자체다 — 다만 "성공률 0% vs 100%" 로 말하면 없는 기능과 비교한 것이 되어
심사에서 되돌려 받는다. **어떻게 말할지는 아직 안 정해졌다** (아래 미결 참고).

## 남은 결정 (팀장)

1. **평가지 척도** — SUS(10문항 표준·비교가능) vs 자체 7점(짧음·과제 밀착).
   변경로그는 "어려웠나 7점"을 원안으로 두되 확정은 아니다
2. **`diagnosis` 과제를 기존 앱에서 어떻게 판정하나** — 대응 화면이 없다
3. **참가자 수·모집** — 표본이 두 자릿수를 못 넘는 전제로 지표를 짰다
4. **녹음 여부** — 하면 동의서가 선행이다
