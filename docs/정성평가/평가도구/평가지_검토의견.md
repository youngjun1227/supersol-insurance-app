# 평가지 검토 — 61문항에서 27문항으로

> 대상: `참고자료/평가지_의견표시이후자료.docx` (팀원 개정안, 61문항)
> 결과: [`평가지.md`](평가지.md) 27문항
>
> **개정안은 앞선 지적을 대부분 반영했다.** 추상적 질문에 보기가 생겼고, 팝업 문항이
> "나중에 하기"에서 **플로우 변경 자체**로 옮겨갔고, 보험 탭 외 질문이 빠졌다.
> 아래는 개정 방향에 대한 것이지 작업을 부정하는 것이 아니다.

## 1. 왜 줄였나 — 61문항은 20~30분에 안 들어간다

| | |
|---|---|
| 1인 배정 시간 | 20~30분 |
| 앱 2개 과제 수행 | 최소 15분 |
| 설문에 쓸 수 있는 시간 | **10분 내외** |
| 61문항 ÷ 10분 | **문항당 약 10초** |

5점 척도 40개를 10초씩 찍으면 참가자는 읽지 않고 가운데를 누른다.
그렇게 나온 "평균 4.1점"은 데이터가 아니다. **문항을 줄이는 것이 정확도를 올린다.**

## 2. 뺀 것과 이유

### ① 알림톡 6문항 (Q51~Q56) — 앱에 없고, 만들지도 않는다

카톡 알림톡 화면이 구현돼 있지 않다. `ClaimSettings` 에 "카카오톡"을 **수신 방법으로
고르는 토글**만 있고 알림톡 화면 자체가 없다 (`src/pages/` 에 해당 라우트 없음).

**2026-09-03 팀장 결정: 알림톡은 구현하지 않는다.** 따라서 이 6문항은 되살릴 여지가
없으므로 완전히 뺀다.

없는 화면을 물으면 참가자는 상상으로 답한다("있으면 편할 것 같아요"). 그건 화면에 대한
평가가 아니라 **아이디어에 대한 찬성**이고, 우리가 재려는 건 그게 아니다.
개정안 Q52·Q53·Q54 가 전부 "~할 것 같나요" 가정형인 것이 그 증거다 —
문항을 쓴 사람도 실물이 없다는 걸 알고 있었다.

⚠️ **9/11 에 참가자가 카톡 알림을 언급하면** 진행자는 "그 부분은 이번에 준비되지
않았어요" 라고만 답한다. 설명하거나 설득하지 않는다.

### ② 같은 것을 반복해 묻는 문항 — 한 표로 합침

개정안은 "찾기 쉬웠나"를 여러 번 물었다:

| 개정안 | 실제로 묻는 것 |
|---|---|
| Q12 찾기 쉬웠나 (기존) | 난이도 |
| Q14 찾기까지 과정이 편리했나 (기존) | 난이도 |
| Q15 위치를 쉽게 파악했나 (기존) | 난이도 |
| Q16·Q18·Q19 (프로토타입) | 같은 것 3번 더 |

6문항이 사실상 한 가지를 묻는다. → **Q9 한 표(양쪽 각 1줄)로 합쳤다.**
같은 걸 여러 번 물으면 응답이 정교해지는 게 아니라 참가자가 지친다.

### ③ 방사형 차트·또래 비교 12문항 → 4문항

Q35~Q46 이 12문항인데, 전부 **"얼마나 도움이 되었나"** 한 방향이다.
도움 정도를 12번 물어도 새로 알게 되는 건 없다. 4문항으로 줄이고,
대신 **반대 방향 1문항(Q21 "부담스럽지 않았나")** 을 넣었다.

### ④ Q50 "신한라이프가 먼저 노출되는 구조" — 문항 자체가 위험

이 문항은 계열사 우대를 참가자에게 **먼저 알려주고** 평가를 받는다.
심사에서 "자사 상품 밀어주기를 사용자에게 확인받았나"로 되돌아온다.
탐색 편의(Q22·Q23)로만 묻고 자사 우선 노출은 문항으로 만들지 않는다.

## 3. 되살린 것 — Q26 "불편했던 점"

원본 검토에서 이런 의견이 있었다:

> Q11. 두 화면을 비교했을 때, 프로토타입에서 오히려 아쉽다고 느낀 점은?
> → **"굳이 저희한테 마이너스가 될 소지가 있는 질문은 안해도 된다고 생각합니다."**

**이 문항은 유지해야 한다.**

- 8명 전원이 좋다고만 한 결과는 **"불리한 건 안 물으셨네요"** 한 마디로 무너진다.
  질문지를 제출하라고 하면 안 물어본 게 그대로 보인다
- 리서치에서 반증을 일부러 찾는 이유가 이것이다 — 확증 편향을 피하지 않으면
  결과가 아니라 자기 확인이 된다
- 불리한 답이 나오는 것이 **이 조사가 정직했다는 증거**다. 발표에서
  "이런 지적도 있었고 이렇게 보완하겠다"가 오히려 강하다

Q12(기존 앱 개선 제안)를 뺀 것은 동의한다 — 우리가 고칠 대상이 아니다.

## 5. 진행자에게 넘긴 것 — 문항이 아니라 관찰

개정안 Q47("가장 먼저 무엇을 누르셨나요")은 **참가자에게 물으면 안 되는 것**이다.
사람은 자기가 뭘 먼저 눌렀는지 정확히 기억하지 못하고, 답하면서 합리화한다.

→ 평가지에서 빼고 **진행자 기록란**으로 옮겼다. 진행자가 보고 적는다.

## 6. 남은 문제

1. **방사형 차트·또래 비교의 위치** — 보장진단 본화면이 아니라 `/diagnosis/briefing` 에 있다
   (`src/pages/Briefing.tsx`). 본화면은 배터리를 쓴다. 참가자가 거기까지 가야
   Q18~Q21 을 물을 수 있다. **못 가면 그 자체가 결과**라 "못 도달"로 기록한다
2. ~~**알림톡**~~ — **해결됨.** 구현하지 않기로 확정(2026-09-03 팀장). 문항 6개 영구 제외

# 2차 수정 (2026-09-03) — 리서치 방법론 감사 반영

27문항 안을 **편향 감사 + 분석 타당성 감사** 두 축으로 다시 검토했다.
결과: 도입 3문항 추가 + 본문 29문항. 주요 변경은 아래.

## A. 가장 컸던 문제 — 상태 A 분기가 평가지에 없었다

상태 A(미보유)는 **다른 화면**을 본다 (`S1-8`). `myInsurance`·`serviceGroups` 가
아예 렌더되지 않고(`FinanceInsurance.tsx:425`), 보장은 전 항목 0이다
(`COVERAGE_A`, `mock.ts:151`).

1차 안은 이걸 반영하지 않아 **최소 8문항이 미보유자에게 성립하지 않았다.**
문항마다 `[보유만]` / `[A·B 분리]` 를 표기하고, 진행자 기록란에 **N/A 칸**을 넣었다.

⚠️ N/A 가 없으면 진행자가 "실패"로 적는다. `diagnosis`(기존 앱에 대응 화면 없음)와
`premium`(상태 A)이 그렇게 집계되면 **기존 앱 성공률이 부당하게 낮아진다** —
우리에게 유리한 편향이고, 클릭 수를 비교에서 뺀 것과 정확히 같은 종류의 문제다.

## B. 과업 지시문이 비대칭이었다 (주 지표 오염)

1차 안:
- 기존: "슈퍼SOL**에서 보험금 청구 기능을 찾아** 청구 화면까지 가주세요" (탐색 과제)
- 우리: "이번엔 이 화면에서 **보험금 청구 안내를 확인하고**…" (안내가 있다는 힌트)

게다가 우리 앱만 `/?popup=claim` 으로 **팝업이 뜬 상태에서 시작**했다.
기존 앱은 홈에서 출발하는데 우리는 목적지 한 걸음 앞에서 출발한 셈이다.

→ **양쪽 다 홈에서 시작하고 지시문을 한 글자까지 통일**했다. 팝업은 과업이 끝난 뒤
Q6 앞에서 따로 보여준다.

## D. 자기보고를 실측으로 바꾼 것

**Q17 방사형 차트** — "얼마나 도움이 되었나"(5점) → **"가장 부족한 영역이 어디인가"**
정오 판정. "8명 중 6명이 정확히 짚었다"는 직접 관찰 근거가 되고,
"평균 4.1점"은 심사에서 무게가 없다.
