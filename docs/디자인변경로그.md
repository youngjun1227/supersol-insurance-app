**티어 전체 매핑 (2026-08-26 확정 — 이걸로 데이터 모델에 `tier` 필드 추가)**:

티어는 기존 `group`(치료비/큰 병/노후·간병/만일)과 **별개 축**이다 — 기준은 "20대 중요도 × 충족 여부"이지 보장 유무가 아니다.

| tier 키 (제안) | 이름 | 항목 (표시 순서 고정) | 카운트 라벨 |
|---|---|---|---|
| `now` | 지금 채우면 좋아요 | 실손의료비 · 입원 — 둘 다 "먼저 볼 항목" 뱃지 | "20대 우선 · 2개 항목" |
| `later` | 여유 있을 때 봐도 돼요 | 수술 · 치과치료 · 심혈관질환진단 · 뇌혈관질환진단 · 치매진단 · 후유장해 | "6개 항목" |
| `covered` | 이미 준비돼 있어요 | 암 진단 | "1개 항목" |
| `notyet` | 지금은 서두르지 않아도 돼요 | 사망 | "1개 항목" |

- **후유장해가 `later`인 것은 의도** — 보유(1,000만) 중이지만 또래 수준(3,000만) 미달이라 `covered` 자격이 없고, 20대 중요도가 낮아 `now`도 아니다. 반례로 입원은 일부 보유인데도 중요도가 높아 `now`. `covered`는 "또래 평균 도달"만 들어간다.
- 접기 규칙: 티어당 앞 3개 표시, 나머지 접힘 — 별도 선정 기준 없음, **티어 내 고정 순서** 필드로 구현
- 카운트 라벨은 티어별 문자열이 다름(`now`만 "20대 우선 ·" 접두) — 데이터에 라벨 통째로 두는 게 안전
- 원본 기록: 디자인 레포 `02_to-be/mock-data.md` §2-3
- 항목 배터리 단계 규칙: **없음 = 0 / 일부 보유 = 30 / 또래 평균 도달 = 100** (60은 현재 미사용 — 실손·수술·치과·심혈관·뇌혈관·치매·사망 0, 입원·후유장해 30, 암 진단 100)

### 5. S6 상품 상세 — 에이전트 진입 버블 ✅ 확정 (2026-08-26)
- 헤더 아래 우측 플로팅: 말풍선 "상품에 대한 궁금한 점 물어보세요!" (primary 채움 pill, 흰 글자 13pt) + **신한 마스코트(쏠·흰 곰)**
- 탭 → 에이전트 대화 화면(S3-F UI 재사용), **상품 문맥 프리셋 프롬프트가 이미 실행된 상태로 도착**: "케어받는암보험의 무배당·갱신형이 무슨 뜻인가요?" → 프리셋 답변 → 추천 칩 "갱신 주기는 어떻게 되나요?"
- ✅ **마스코트 사용은 2026-08-26 멘토 구두 허락됨** (이전 금지 규칙 해제).
- ✅ **말풍선은 계속 떠 있지 않는다 (2026-08-28 팀장 결정)** — 화면 폭의 65%를 차지해 상품명 위를 덮는다.
  문구 2개를 순서대로 보여준 뒤 접고 **마스코트만 남긴다**. 접힌 뒤에도 탭 영역은 그대로라 진입점은 유지된다.
  | 순서 | 문구 | 시점 |
  |---|---|---|
  | 1 | 상품에 대한 궁금한 점 물어보세요! | 진입 직후 ~2.6s |
  | 2 | **AI가 쉽게 설명해줘요** | 2.6s ~ 5.2s |
  | — | (접힘 — 마스코트만) | 5.2s ~ |
  - **말주머니 폭이 문구에 맞춰 늘었다 줄어든다** — 문구마다 폭이 다르다(174 vs 108).
    숨은 span 으로 각 문구의 자연 폭을 미리 재서 인라인 `width` 로 넣고, 글자는 따로 페이드인 한다.
    ⚠️ **`max-width` 로는 안 된다** — 실제 폭은 내용이 정하고 `max-width` 는 상한일 뿐이라,
    글자가 바뀌면 폭이 한 프레임에 튄다(202 → 136). `width` 를 직접 트랜지션해야 이어진다.
    ⚠️ 측정용 span 에는 **버블과 같은 좌우 패딩(14px)** 을 줘야 한다 — 없으면 28px 좁게 재서 글자가 잘린다.
  - `prefers-reduced-motion` 이면 순환하지 않고 첫 문구만 둔다 (전역 CSS 는 트랜지션만 줄여줘 JS 타이머는 따로 본다)
  - 스크린리더에는 `sr-only` 로 첫 문구를 항상 노출한다 — 문구가 바뀌어도 안내가 흔들리지 않게
  - ⚠️ **상품을 바꿔 가며 볼 때 재마운트되지 않아** 첫 상품에서 접힌 뒤 영영 안 뜨는 버그가 있었다.
    `resetKey`(상품 id)로 화면이 바뀌면 처음부터 다시 돌게 했다
- ✅ **마스코트 상호작용 (2026-08-28 팀장 결정 · #53)** — 눌림 + hover + 상시 미세 모션
  | 상태 | 반응 | 어디서 보이나 |
  |---|---|---|
  | 누름 `:active` | 마스코트 `scale(0.92)` · 말풍선 `opacity 0.85` | **폰·데스크톱 둘 다** |
  | 마우스 올림 `:hover` | 마스코트 `scale(1.08)` | 데스크톱만 (`@media (hover: hover)`) |
  | 접힌 뒤 상시 | 위아래 3px `mascotFloat` 2.8s | 폰·데스크톱 둘 다 |
  - ⚠️ **폰에는 hover 가 없다** — 9/11 참가자도 심사위원도 폰에서 QR 로 연다. `:active` 가 실제로 보이는 유일한 피드백이라 그쪽을 먼저 맞췄다. 눌림 값(`opacity 0.85`)은 공용 `Button` 과 같은 계열이다
  - **문구가 떠 있는 동안에는 상시 모션이 돌지 않는다**(`data-idle`) — 읽는 걸 방해하지 않게. 진폭 3px 도 같은 이유다
  - ⚠️ **떠다님과 크기 변화를 다른 요소에 걸었다** — 둘 다 `transform` 이라 한 요소에 두면 애니메이션이 이겨서 `scale` 이 안 먹는다. 감싼 span 이 떠다니고 이미지가 커지고 작아진다
  - `prefers-reduced-motion` 이면 상시 모션은 끈다 — 전역 CSS 는 duration 만 줄여서 `infinite` 는 계속 돈다

### 계측 수정 — tap 의 screen 이 'unknown' 이던 문제 (2026-08-27, 팀장 · #38)

팀원 A 가 S1 계열 전수 점검 중 찾았다. **탭 기록의 절반이 `screen:'unknown'` 으로 쌓이고 있었다.**

원인은 트리 구조다. 화면 컴포넌트는 자기 `<AppShell>`(=`<ScreenProvider>`)을 **만드는** 쪽이라
React 트리에서 Provider 보다 위에 있다 → 화면 파일이 직접 부른 `useTrack()` 은 `ScreenContext` 를
못 읽고 기본값을 가져갔다. 공용 컴포넌트(`Header`·`TabBar`·`Button`·`BottomSheet`)는 Provider
안쪽이라 멀쩡했고, 그래서 에러 없이 지금까지 안 드러났다.

**고친 방법** — `analytics.ts` 에 `currentScreen` 모듈 변수를 두고 `useScreenView()` 가 진입 때마다
갱신한다. `track()` 은 `screen` 이 `'unknown'` 으로 오면 이 값으로 채운다.
화면 파일 20개를 고치는 대신 공용 2파일만 고쳤다 — **앞으로 새로 만드는 화면도 자동으로 커버된다.**
(대안이던 "`useTrack('화면이름')` 로 이름을 넘긴다"는 화면 20개 수정 + 새 화면마다 누락 위험이 남고,
"라우터에서 `<ScreenProvider>` 로 감싼다"는 **S1 이 한 라우트에 이름 3개라 불가능**했다.)

⚠️ **`?state=` 별 진입은 `AppShell name` 으로 갈린다는 전제가 tap 행에서도 이제 성립한다.**
9/11 데이터가 이미 `unknown` 으로 쌓인 뒤에는 고쳐도 소용이 없어 테스트 전에 넣는다.

### S2 카테고리 필터 — '전체' 칩 왼쪽 고정 (2026-08-28, 팀장)

카테고리를 고르면 선택 칩이 앞으로 스크롤되면서 **'전체' 칩이 화면 밖으로 나갔다**
(치아 선택 시 `right=-287`). 필터를 푸는 방법이 사라진다.

'전체' 를 `position: sticky` 로 왼쪽에 고정하고 나머지 칩만 그 뒤로 지나가게 했다.

**최종 구조 — '전체' 를 스크롤 영역 밖으로 뺐다.**

처음에는 같은 스크롤 영역 안에서 `sticky` 로 붙였는데, 지나가는 칩이 여백에 비쳐
가림막을 겹겹이 쌓아야 했고(래퍼 배경 · `left` 음수 보정 · `::after` 가림막),
그렇게 해도 **선택 칩을 아래 회사 칩 행과 정렬할 수 없었다** — `sticky` '전체' 와
선택 칩이 같은 자리(20px)를 다투기 때문이다.

행을 둘로 나눠 해결했다:
```
.catRow  = [고정 '전체'] + [.chipRow 스크롤 영역]
```
- '전체' 는 스크롤 밖이라 **항상 보이고 겹침·비침이 없다** (가림막 불필요)
- 두 행의 '전체' 칩이 **세로로 정확히 정렬**된다 (둘 다 `left=20`)

### S3-F 대화 — 마지막 답변이 입력 바에 가리던 것 (2026-08-29, 팀장)

질문을 이어서 하면 **마지막 답변이 입력 바 뒤로 들어가** 안 보였다 (#70).
문서 1626 인데 스크롤이 651 에서 멈추고, 답변이 입력 바를 60px 침범했다.

원인이 **두 개** 였고 둘 다 고쳐야 했다 — 하나만 고쳐서는 안 됐다.

**1) 여백이 입력 바보다 작았다.** 주석은 "입력 바 높이(84)보다 커야 한다" 인데
실제 값은 `calc(var(--space-8) * 2)` = **64** 였다. 의도와 코드가 어긋나 있었다.
입력 바와 **같은 토큰으로 계산**해 다시 어긋나지 않게 했다:
`--h-btn(48) + --space-3(12) + --space-6(24) = 84` + 한 칸(`--space-4`).

**2) `scrollIntoView` 가 맨 아래까지 못 갔다.** 대화 끝의 빈 div(높이 0)에
`block:'end'` 를 걸었는데, 그 점을 **창 아래 끝에 맞추는 게 곧 입력 바 뒤**다
(입력 바는 `position:fixed` 라 문서 높이에 안 잡힌다).
`window.scrollTo(문서 끝)` 로 바꿨다. 빈 div 는 쓰임이 없어져 지웠다.

⚠️ 여백만 고쳤을 때 `padding-bottom` 은 100 으로 늘었는데 **여전히 가렸다** —
스크롤이 651 에 멈춘 채라서다. 두 원인이 독립이라는 걸 이 검증에서 확인했다.

질문 8개까지 이어서 확인했다 (1개째 여유 294 · 2~8개째 166). 대화가 짧을 때
불필요한 스크롤이 생기지 않고 배경 그라데이션도 그대로다.
### 화면을 옮기면 맨 위에서 시작한다 (2026-08-29, 팀장)

화면을 옮겨도 **스크롤 위치가 그대로 남아** 새 화면이 중간부터 시작했다.
상품 목록에서 1200px 내려가 상품을 누르면 상세 화면이 70px 지점에서 시작해
제목이 이미 지나간 상태로 도착한다.

스크롤이 있는 화면 **9개 전부** 같은 상태였다. SPA 는 페이지를 새로 부르지 않아서
React Router 가 대신 올려주지 않는다 — 앱에 되돌리는 코드가 아예 없었다.

`useScrollTop()` 을 `App` 에 하나 넣었다.

**뒤로 가기도 예외 없이 맨 위로 올린다 (팀장 결정).** 목록으로 돌아올 때 보던 자리를
유지하는 편이 자연스럽다는 의견이 있었지만, 9/11 참가자가 화면 중간에서 시작해
길을 잃는 쪽이 더 큰 문제다.

⚠️ 뒤로 가기는 훅만으로는 안 됐다 — **브라우저가 스크롤을 자기가 되돌린다**
(`history.scrollRestoration` 기본 `'auto'`). 그 복원이 훅보다 나중에 일어나서
뒤로 갈 때만 1000px 이 그대로 남았다. `'manual'` 로 꺼서 해결했다.

⚠️ 스크롤하는 것은 `AppShell` 의 `<main>` 이 아니라 **창(window)** 이다 —
`main` 에 `overflow-y:auto` 가 있지만 높이 제한이 없어 내용만큼 늘어나고,
넘치는 건 문서 전체다. `main.scrollTop = 0` 으로는 안 움직인다.

`useLayoutEffect` 로 그리기 전에 올린다 — `useEffect` 면 내려간 화면이 한 프레임
비쳤다가 튀어 오른다.

앞으로 가기 포함 9개 경로에서 확인했다.

### 가로 러버밴드 차단 — overscroll-behavior 양축으로 (2026-08-29, 팀장)

### 1-2. 지표 위상 재정의 — 클릭 수·시간은 비교에서 뺀다 (2026-08-27, 팀장)

**측정 방법이 양쪽에서 달라 비교가 성립하지 않기 때문이다.**

우리 구현은 계측이 자동이지만 **기존 슈퍼쏠은 남의 앱이라 코드를 못 건드린다.**
한쪽은 기계가 정확히 세고 한쪽은 진행자가 눈으로 세면, 그 차이 자체가 결과를 만든다 —
기존 앱에서 진행자가 한 번 놓치면 실제로는 우리가 나쁜데 좋아 보인다.
이건 오차가 아니라 **우리에게 유리한 방향의 편향**이라 발표에서 방법론을 물으면 무너진다.

| 지표 | 비교에 쓰나 | 측정 방법 |
|---|---|---|
| **과제 성공률** | ✅ 주 근거 | 양쪽 동일 — 도착 여부 + 구두 응답 |
| **주관 평가(평가지)** | ✅ 주 근거 | 양쪽 동일 — ★평가지 미작성 |
| 클릭 수 · 시간 | ❌ **비교 안 함** | 우리 쪽만 자동 — 내부 진단용 |

- 표본이 두 자릿수를 못 넘어 클릭 수 평균은 어차피 통계적 주장이 안 된다
  ("평균 4.2 vs 5.1"은 참가자 2명만 바뀌어도 뒤집힌다).
  반면 **"기존 앱에서 3명이 못 찾았는데 우리 것에서는 전원이 찾았다"** 는 성공률로 그대로 말할 수 있다.
- 클릭 수를 꼭 비교해야 할 상황이 되면 **양쪽 다 화면 녹화로 세는 방법**만 정당하다
  (측정 방법을 통일해야 한다). 비용이 커서 기본값으로 두지 않는다.

**계측의 용도가 "증명"에서 "발견"으로 바뀐다.** 비교 근거로는 안 쓰고,
우리 앱 안에서 어디서 헤맸는지 찾는 데 쓴다 — 예: "8명 중 5명이 보험금 청구를 먼저 눌렀다,
우리 라벨이 오해를 부른다". 이건 기존 앱과 비교할 필요가 없는 정보라 한쪽만 있어도 성립한다.

**그래서 계측 코드는 그대로 둔다** (수집 유지 · 유지 비용 0). 다만 아래는 전부 **평가지 확정 후로 보류**한다:
지표 가중치 · `/moderator` 기기 구성 · `taskId` 과제 경계 처리 · 외부 전송(Google Sheets 등).
⚠️ 화면을 새로 만들 때 `tid()` 계측을 붙이는 규칙은 **보류 대상이 아니다** — 나중에 소급하면 화면을 다 다시 열어야 한다.

## 공용 셸 — 헤더 sticky 가 전 화면에서 안 붙던 문제 (2026-09-05, 팀원 B)

스펙 §4 "본문 스크롤 시 헤더는 sticky" 인데, 실제로는 모든 화면에서 헤더가 본문과 같이 올라가 사라졌다
(393×600 뷰포트로 S1·S6-A 스크롤 실측: 헤더 top −400). 폰에서 긴 화면을 내리면 뒤로가기·제목이 없어진다.

원인은 `AppShell .shell` 의 `overflow-x: hidden` 한 줄 — overflow 가 visible 이 아니면 그 상자가 스크롤
컨테이너가 되어(overflow-y 는 auto 로 계산) `.header` 의 sticky 기준이 뷰포트가 아니라 `.shell` 이 된다.
`.shell` 은 `min-height` 라 내용만큼 늘어나고 실제로는 창이 스크롤하니 sticky 가 아무 일도 안 했다.

`overflow-x: clip` 으로 바꿨다 — 가로 넘침은 똑같이 자르되 스크롤 컨테이너를 만들지 않아 sticky 가 뷰포트에
붙는다 (Safari 16+ · Chrome 90+ · Firefox 81+). 가로 스크롤(#147)도 그대로 안 생긴다 (S1·S6-A 실측 393).
⚠️ 공용 셸은 팀장 소유 — 발견·수정 보고. 헤더가 붙기 시작하면 sticky 헤더 아래에 오는 요소(S6-A 버블 dock 등)의 top 기준이 실제로 의미를 갖는다.
